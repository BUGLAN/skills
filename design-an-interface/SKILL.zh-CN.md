# 设计一个接口

源自《A Philosophy of Software Design》（软件设计哲学）中的 "Design It Twice"：你的第一个想法几乎不可能是最好的。生成多个截然不同的设计，然后比较。

## 工作流

### 1. 收集需求

设计之前，先弄清楚：

- [ ] 这个模块解决什么问题？
- [ ] 调用方是谁？（其他模块、外部用户、测试）
- [ ] 关键操作有哪些？
- [ ] 有什么约束？（性能、兼容性、既有模式）
- [ ] 什么该藏在内部，什么该暴露出去？

开口问："这个模块需要做什么？谁来用它？"

### 2. 生成设计（并行子代理）

用 Task 工具**同时**派出 3 个以上子代理。每个子代理必须产出**截然不同**的方案。

```
每个子代理的提示词模板：

为以下模块设计接口：[模块描述]

需求：[收集到的需求]

本设计的约束：[给每个代理分配不同的约束]
- 代理 1："把方法数压到最少——目标最多 1-3 个方法"
- 代理 2："把灵活性放到最大——支持尽可能多的用例"
- 代理 3："为最常见的情况做优化"
- 代理 4："从【某个具体范式/库】汲取灵感"

输出格式：
1. 接口签名（类型/方法）
2. 用法示例（调用方如何使用）
3. 这个设计把什么藏在了内部
4. 这条路的取舍
```

### 3. 展示设计

展示每个设计时包含：

1. **接口签名** —— 类型、方法、参数
2. **用法示例** —— 调用方实际怎么用
3. **它隐藏了什么** —— 留在内部的复杂度

按顺序逐个展示，让用户在比较之前先消化每一种方案。

### 4. 比较设计

全部展示完后，从以下维度比较：

- **接口简单度**：方法更少、参数更简单
- **通用 vs 专用**：灵活性 vs 聚焦
- **实现效率**：这个形态是否允许高效的内部实现？
- **深度**：小接口藏住大复杂度（好）vs 大接口配薄实现（坏）
- **正确使用的容易度** vs **误用的容易度**

用行文讨论取舍，不要用表格。突出设计方案之间分歧最大的地方。

### 5. 综合（Synthesize）

最好的设计常常融合多个选项的洞见。要问：

- "哪个设计最贴合你的主要用例？"
- "其他设计里有什么元素值得吸收进来？"

## 评估标准

出自《A Philosophy of Software Design》：

**接口简单度**：方法更少、参数更简单 = 更容易学习、更容易正确使用。

**通用性**：无需改动就能应对未来的用例。但警惕过度泛化。

**实现效率**：接口形态是否允许高效实现？还是逼出别扭的内部结构？

**深度**：小接口藏住大复杂度 = 深模块（好）。大接口配薄实现 = 浅模块（避免）。

## 反模式

- 不要放任子代理产出雷同的设计——强制彻底不同
- 不要跳过比较环节——价值就在对比之中
- 不要动手实现——这里只关心接口形态
- 不要按实现工作量来评估
