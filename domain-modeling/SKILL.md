# 领域建模（Domain Modeling）

在设计过程中主动构建并打磨项目的领域模型。这是一项*主动性*纪律：挑战用词、构造边界场景，并在概念成形的当下就把词汇表和决策写下来。（只是*读* `GLOSSARY.md` 取词不算这个 skill——那只是任何 skill 都能顺手做的一件事。这个 skill 用于你正在**改变**模型、而不只是消费它的时候。）

## 文件结构

多数仓库只有一个上下文（context）：

```
/
├── GLOSSARY.md
├── docs/
│   └── adr/
│       ├── 0001-event-sourced-orders.md
│       └── 0002-postgres-for-write-model.md
└── src/
```

如果根目录存在 `GLOSSARY-MAP.md`，说明这个仓库有多个上下文。该 map 指向每个上下文所在的位置：

```
/
├── GLOSSARY-MAP.md
├── docs/
│   └── adr/                          ← 全局决策
├── src/
│   ├── ordering/
│   │   ├── GLOSSARY.md
│   │   └── docs/adr/                 ← 该上下文专属的决策
│   └── billing/
│       ├── GLOSSARY.md
│       └── docs/adr/
```

按需惰性创建文件：只有真有内容要写时才建。如果还没有 `GLOSSARY.md`，就在第一个术语被敲定时创建它。如果还没有 `docs/adr/`，就在第一个 ADR 需要出现时创建它。

## 会话过程中

### 对照词汇表提出质疑

当用户使用的术语与 `GLOSSARY.md` 里既有的语言冲突时，立刻指出来。“你的词汇表把 'cancellation' 定义为 X，但你现在的意思似乎是 Y。到底是哪个？”

### 磨掉模糊的表达

当用户使用含糊或含义过载的术语时，提出一个精确的规范术语。“你说的是 'account'——你指的是 Customer 还是 User？这是两个不同的东西。”

### 讨论具体场景

在讨论领域关系时，用具体场景做压力测试。构造能探测边界情况的场景，逼用户把概念之间的边界说清楚。

### 与代码交叉验证

当用户陈述某件事如何运作时，检查代码是否同意。如果发现矛盾，就摆出来：“你的代码会取消整个 Order，但你刚说支持部分取消。哪个是对的？”

### 就地更新 GLOSSARY.md

当一个术语被敲定时，当场更新 `GLOSSARY.md`。不要攒到最后批量处理：概念一出现就捕获。格式见 [GLOSSARY-FORMAT.md](./GLOSSARY-FORMAT.md)。

`GLOSSARY.md` 里不应有任何实现细节。不要把 `GLOSSARY.md` 当成 spec、草稿纸，或存放实现决策的仓库。它只是一份词汇表，仅此而已。

### 谨慎地提议写 ADR

只有以下三条同时成立时，才提议创建 ADR：

1. **难以回头**：以后改变主意的代价是可观的
2. **没有上下文就会让人意外**：未来的读者会想“他们当初为什么这么做？”
3. **是真实取舍的结果**：确实存在其他可选方案，而你基于具体理由选了其中一个

三条缺任何一条，就跳过 ADR。格式见 [ADR-FORMAT.md](./ADR-FORMAT.md)。
