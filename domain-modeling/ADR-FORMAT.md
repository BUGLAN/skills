# ADR 格式

ADR 放在 `docs/adr/` 下，使用连续编号：`0001-slug.md`、`0002-slug.md`，依此类推。

`docs/adr/` 目录惰性创建：只有第一个 ADR 需要出现时才建。

## 模板

```md
# {Short title of the decision}

{1-3 sentences: what's the context, what did we decide, and why.}
```

就这样。一个 ADR 可以只有一段话。它的价值在于记录**做过**这个决策、以及**为什么**，而不在于把各个小节填满。

## 可选小节

只有当它们确实带来价值时才加。多数 ADR 用不上。

- **Status** frontmatter（`proposed | accepted | deprecated | superseded by ADR-NNNN`）：当决策后来会被重新审视时有用
- **Considered Options**：只有当被否掉的方案值得记住时才写
- **Consequences**：只有当存在不明显、需要点出来的下游影响时才写

## 编号

扫一遍 `docs/adr/`，取现有最大编号加一。

## 什么时候该提议写 ADR

下面三条必须同时成立：

1. **难以回头**：以后改变主意的代价是可观的
2. **没有上下文就会让人意外**：未来的读者会看着代码想“他们当初到底为什么这么做？”
3. **是真实取舍的结果**：确实存在其他可选方案，而你基于具体理由选了其中一个

如果一个决策很容易回头，就跳过：你回头改掉就是了。如果它不让人意外，没人会好奇为什么。如果根本不存在别的方案，那除了“我们做了显而易见的那件事”之外也没什么可记录的。

### 哪些算数

- **架构形态。** “我们用 monorepo。”“写模型是事件溯源的，读模型投影到 Postgres。”
- **上下文之间的集成模式。** “Ordering 与 Billing 之间通过领域事件通信，而不是同步 HTTP。”
- **带有锁定效应的技术选型。** 数据库、消息总线、认证服务商、部署目标。不是每个库都算：只算那些换掉要花一个季度的。
- **边界与范围决策。** “Customer 数据归 Customer 上下文所有；其他上下文只按 ID 引用。”明确说“不”和明确说“是”同样有价值。
- **对显而易见路径的刻意偏离。** “我们用裸 SQL 而不是 ORM，因为 X。”凡是理性读者会假设成相反做法的地方都算。这类记录能阻止下一位工程师去“修好”一个本来就有意为之的设计。
- **代码里看不出来的约束。** “因为合规要求，我们不能用 AWS。”“因为合作方 API 合约，响应时间必须低于 200ms。”
- **被否掉的方案，且否掉的理由不明显。** 如果你考虑过 GraphQL，出于一些微妙理由选了 REST，就记下来；否则半年后会有人再提一次 GraphQL。
